# Redis 源码项目分析报告

## 一、项目定位

这是一个**个人维护的 Redis 源码学习与改造仓库**（不是业务项目）：

- 上游：`xindoo/redis`（Redis 官方仓库 fork 的**中文注解版**），你又从它 fork 出自己的仓库做二次整理。
- 核心目的：**源码 + 中文注释 + 服务端代码模块化拆分**，用于系统性阅读/调试 Redis 内核。
- 版本：`src/version.h` 中 `REDIS_VERSION "6.0.0"`、`REDIS_VERSION_NUM 0x00ffffff`（unstable 标记）；但代码里已包含 `lolwut6.c`、`tracking.c`（客户端缓存）、`tls.c`、`sha256.c`、`timeout.c` 等 **6.2 期特性**，说明实际基线是 Redis 6.x unstable 快照，version.h 未同步。
- 构建产物自报：`Redis server v=6.0.0 sha=33d920bd:0 malloc=libc bits=64`。

## 七、发现的问题与建议

1. **`server.h` 仍有 1950 行**，是拆分后新的"巨石"。建议按同样思路拆出 `server_struct.h`（结构体/枚举）、`server_api.h`（函数声明）、`server_globals.h`，或至少把命令表相关声明抽到 `server_commands.h`。
2. **`version.h` 与源码版本不符**：标 6.0.0 但有 6.2 特性（`lolwut6.c` 已进 Makefile）。学习/引用时容易误判 API 版本，建议核对并修正到真实基线。
3. **`src/` 下混入了运行产物**：`appendonly.aof`、`dump.rdb`、`nodes.conf`、`redis.log`、`redis.conf`。虽部分被 `.gitignore` 覆盖，但 `redis.conf` / `nodes.conf` 是显式跟踪的，建议清理以免与仓库根的 `redis.conf` 混淆。
4. **`document/` 目录为空**：README 承诺了"源码 + 中文注释 + 系列博文"三位一体，但本地还没有笔记产出，建议把拆分后的模块地图写进去（可直接复用本报告的表格）。
5. **拆分后的回归风险**：`server.c` 拆分涉及跨文件符号可见性，目前 `make` 通过，但建议跑一次 `./runtest` 全量回归（尤其是 `unit/introspection`、`unit/info`、`unit/other`、`integration/replication`）确认行为零差异。
6. 构建依赖 jemalloc/lua 等并未预编译成库，`make distclean` 后重建耗时较长，可考虑固化一次 `make MALLOC=libc` 的构建脚本。
